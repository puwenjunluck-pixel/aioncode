## 1. 多组件边界插桩协议（怀疑跨层 bug 时）

不要逐层猜。在**每一层边界**同时打印进/出数据，跑**一次**复现定位坏在哪层，再深入该层：

1. 列出数据流经的层（如 UI → API handler → service → DB）
2. 在每个边界插入带层名前缀的日志：进入时打输入，离开时打输出
3. 跑**一次**复现用例，按顺序通读日志 — 第一个「进对出错」的层就是目标层
4. 只深入该层调查；其余插桩在修复后移除

```bash
# 通用示例：每层边界一行带前缀的快照，一次运行后通读
echo "[LAYER:api-in]  payload=${payload}"  >> /tmp/trace.log
echo "[LAYER:svc-out] result=${result}"    >> /tmp/trace.log
grep "LAYER:" /tmp/trace.log   # 找第一个值由对变坏的边界
```

> 一次插桩跑一遍 > 五次猜测各改一处。插桩是证据收集，不是修复尝试。

## 2. 反向追踪（从错误现场向上）

从报错/坏值出现的位置出发，沿调用链**向上**逐级检查：「这个值在这里已经错了吗？」
找到**第一个**值由对变错的点 — 那里（或其直接输入）才是根因。在错误现场打补丁 = 症状式修复。

## 3. 时序类 bug

- 固定 `sleep N` 是猜测，不是同步。用**条件等待**替代：轮询目标状态直到满足或超时
- 复现概率 < 100% 时先提高复现率（放大并发 / 缩小超时 / 固定随机种子），再调查
- 「加了 sleep 就好了」= 掩盖时序竞争，不是修复 — 找到真正的事件顺序依赖并显式等待它

## 4. 「真环境性问题」合法出口

调查证明 bug 是**环境 / 时序 / 外部依赖**问题（不是代码逻辑错误）时：

1. 记录调查过程：做过哪些插桩、排除了哪些假设、证据指向什么
2. 用 retry / timeout / 监控告警处理，而不是硬修不存在的代码 bug
3. 这是**合法 DONE**，不是失败 — 在 summary 中如实标注

> ⚠️ 95% 的「查不到根因」是调查不完整，不是真环境问题。引用本出口之前，先完整过一遍第 1 节插桩协议 — 没插过桩就说「环境问题」= 合理化。
